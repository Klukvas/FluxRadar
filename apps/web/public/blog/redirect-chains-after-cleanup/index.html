Redirect chains and 404s after a content clean-up

Removing outdated pages is healthy, until it leaves broken links and redirects that pass through five addresses. How to decide for each page and check the result.

Published and checked: November 26, 2026

Sooner or later every site collects old promotions, closed job ads, discontinued products and duplicate articles. When you remove them, two problems tend to appear: links that lead nowhere, and redirect chains that have grown with every change of structure. This article is about the decisions during a clean-up and the checks afterwards. How to work through a single broken-link finding is covered in our knowledge base (in Ukrainian).

Three choices for every removed page

Before deleting anything, list the addresses and pick one decision for each:

Situation What to do
Another page genuinely replaces it A permanent redirect (301 or 308) to that page
The page is gone for a short time A temporary redirect (302 or 307)
Nothing replaces it A 404 or 410 response

Google explains the difference: a permanent redirect is a strong signal that the new address should be treated as the main one, while a temporary redirect keeps the old one in results. Use a permanent redirect only when you are sure you will not change it back.

For Google there is no difference between 404 and 410. Its documentation says all 4xx errors except 429 are treated the same: indexed addresses that return one are removed from the index, and these codes have no effect on crawl rate. So pick whichever code your team finds easier to maintain, and do not worry that an honest 404 will "hurt" the site.

The list is easiest to build from a few sources: the current sitemap, a page export from your CMS and an analytics report of pages that still get visits. Mark pages that other sites link to or that people bookmark: that is where the redirect decision matters most. Keep the list, because you will need it for the check.

Why not send everything to the home page

The easy option is to redirect every removed page to the home page or a broad category. But people followed the link for something specific: a manual for an old model, the terms of a promotion, an article. They will not find it on the home page, and they will probably leave.

The second trap is a page that says "product not found" but answers with a 200 code. Google may flag such a page as a soft 404: technically it works, but its content is an error. It is better to return the true status straight away.

A good 404 page is still useful. Say briefly that the content is gone, and offer search and a few main sections. That helps the visitor without misleading search engines.

How chains grow over the years

A chain is when one address leads to another, then to a third, and only then does the page open. Almost nobody builds one on purpose. An illustrative example of how it happens:

  • 2019: the site moves to HTTPS, so http:// redirects to https://;
  • 2021: the www prefix is dropped, adding another rule;
  • 2023: a language folder such as /en/ is added;
  • 2026: a service page is renamed.

Each rule is correct on its own. But an old link from a partner's site now passes through four hops. According to Google's documentation, Googlebot generally follows up to 10 redirect hops, so search will probably still reach the page. Each hop, though, is a separate request and a delay for a person, especially on mobile data, and a loop where addresses point at each other never opens at all.

The fix is to flatten the chain: every old address should point straight at the final one. Internal links, menus and the sitemap should use the final address with no redirect at all. The redirect stays for external links and bookmarks.

Server-side redirects are the reliable kind

Google calls a server-side redirect the best way to send both people and search to the right page. It treats an instant meta refresh as a permanent redirect and a delayed one as temporary. Redirects done by a script in the browser are recommended only when the other options are not available: Google runs that code after crawling, but rendering can fail.

For a site owner, this comes down to one question for the developer or hosting provider: where do our redirect rules live, and who reviews them after each change of structure? Chains appear most often when rules are scattered across a CMS plugin, the server configuration and a CDN.

A plain spreadsheet helps: old address, new address, date and reason for the change. When the page is renamed again a few years later, the team can see every old address that should now point straight at the new one, instead of adding another link to the chain.

Checking after a clean-up

The best check uses the list you made before deleting. For each address, confirm that:

  • the status matches the decision: 301/308 where there is a replacement, 404/410 where there is none;
  • the redirect reaches the final page in a single hop;
  • the final page really delivers what the old link promised.

Then check the site as a whole: no links to removed addresses left in menus, articles or product cards, and none in the sitemap. Also open a few old addresses with the http:// and www variants, since that is where extra hops usually hide. You can see the chain of responses in the Network tab of the browser's developer tools or in a crawler report.

Repeat the check a few weeks later. If you have access to Search Console, review the pages reported as 404 and soft 404. If your hosting provides server logs, see which missing addresses are requested most often. An old page that people still look for is a reason to reconsider whether a fitting replacement exists. Pages nobody opens can safely stay at 404.

What FluxRadar checks

These checks are part of the Basic and Complete plans and run on the pages the crawl actually opened:

  • Redirect chain or loop. A finding appears when an address goes through two or more hops before the final response. A single redirect, such as HTTP to HTTPS, counts as normal. A loop or an endless chain is a finding too.
  • Page does not answer with HTTP 200. A crawled page ended with a code of 400 or above.
  • Links to pages that return an error. An internal link points at an address that answered 4xx or 5xx during the crawl. The finding names the page that holds the link.

FluxRadar only sees addresses that something on the site links to or that you add to the crawl. Old addresses reached only from other sites or bookmarks are not something it finds on its own, so check those against your own list. The tool also does not decide whether the page a redirect leads to is the right one.
