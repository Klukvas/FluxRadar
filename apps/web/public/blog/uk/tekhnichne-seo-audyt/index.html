Технічний SEO-аудит без доступу до адмінки

Публічний аудит охоплює лише те, що бачить пошуковий бот або звичайний відвідувач без логіна. Це обмеження є перевагою: знахідки відтворювані, а докази можна зберегти й перевірити повторно після виправлень.

1. Перевірте межі краулінгу

Завжди починайте з канонічного HTTPS-домену. Переконайтесь, що robots.txt існує, читається й не закриває важливі розділи сайту. Перевірте XML-карту сайту: чи вона оголошена в robots.txt, чи статус-коди всіх URL у ній дорівнюють 200.

GET https://example.com/robots.txt 200 OK Sitemap: https://example.com/sitemap.xml GET https://example.com/sitemap.xml 200 OK URLs in sitemap: 142 Reachable: 138 4xx/5xx: 4

2. Чи пояснює кожна сторінка саму себе?

Кожна важлива сторінка повинна мати:

  • Унікальний, змістовний <title> (30–60 символів)
  • meta description, що відповідає змісту сторінки
  • Один <h1>, узгоджений із заголовком сторінки
  • Канонічний URL (rel=canonical) при множинних версіях
  • Основний контент, доступний у вихідному HTML (не лише через JavaScript)

3. Воронка сторінок — де губляться ресурси

На практиці більшість сайтів губить значну частину сторінок ще на етапі краулінгу. Діаграма нижче ілюструє типовий розподіл для сайту середнього розміру.

4. Структуровані дані як підтверджуючий сигнал

Розмітка Schema.org повинна описувати те, що видно на сторінці. Перевіряйте три речі:

  1. Тип відповідає сторінці — Article для статей, Product для товарів.
  2. Значення збігаються з видимим контентом — заголовок у JSON-LD має відповідати тегу <h1>.
  3. Немає заблокованих ресурсів — якщо сторінка закрита в robots.txt, валідатор не зможе її отримати.

5. Фіксуйте докази, а не лише оцінки

Корисний аудитний звіт містить: URL-адресу, статус-код, знайдений сигнал (або його відсутність), часову мітку та конкретний наступний крок. Без збереженого доказу неможливо підтвердити, що виправлення спрацювало.
