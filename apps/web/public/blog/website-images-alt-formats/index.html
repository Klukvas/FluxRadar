Website images: alt text, formats and lazy loading

Product photos, logos and banners make a site feel alive, but they can also slow it down and leave some visitors without the content. Four things to check in every template.

Published and checked: November 26, 2026

Images on a website do different jobs. One shows a product, another works as a button, a third is pure decoration. That job decides what text the image needs, which format to save it in and when the browser should load it. Below are practical rules for a site owner, plus the specific attributes to agree with your developer. The examples are illustrative.

Alt text is written for people

The alt attribute is the text that stands in for an image when it cannot be seen: a screen reader reads it out, and the browser shows it if the file fails to load. So start with one question: what would someone who cannot see the picture miss?

The W3C alt decision tree gives a simple sequence:

  • Decorative images (a background pattern, a divider) get an empty alt="", so assistive technology skips them.
  • Images that are links or buttons describe where the link goes or what happens, not what the icon looks like. A magnifying glass in the header is "Search", not "magnifying glass".
  • Informative photos get a short description of the point: "Black coffee machine with a milk jug on a kitchen counter".
  • Images of text: if that text appears nowhere else on the page, put it in the alt.
  • Complex graphics (charts, diagrams) need more than a short alt: give the same information as text or a table nearby.

Google also asks for useful alt text that fits the page's context and warns against filling it with keywords, which makes for a poor experience and can look like spam. Note that an empty alt and a missing alt are different. Empty means "this is decoration"; with no attribute at all, a screen reader may read out the file name instead.

A quick self-check: open a product or service page and read only the alt texts, one after another. If they tell you what is shown and what can be clicked, you are fine. If you see "IMG_2041", "photo" or the same description under every picture, the template needs a look. In most CMSs alt text is set in the media library, so fixing one file fixes it everywhere that file is used.

Images that search can find

If a photo should help people find a product or service, make it an ordinary <img> element with its address in the src attribute. Google states plainly that it does not index CSS images, such as a background-image. That is fine for a decorative background, not for a product photo.

A few more points from Google's documentation:

  • Use short, descriptive file names: black-coffee-machine.jpg beats IMG00023.JPG.
  • If you serve several sizes with srcset or <picture>, always keep a fallback address in src: not every browser or crawler understands those attributes.
  • Make the file extension match the real file type.

Formats for photos, logos and icons

Google Search supports images in BMP, GIF, JPEG, PNG, WebP, SVG and AVIF. So choosing a format is mostly about page weight and image quality, not about being found.

What the image shows What to use
Product, interior or team photos WebP or AVIF, with JPEG as the fallback
Logo, icon, diagram SVG, when a vector version exists
Screenshots, text, sharp lines Lossless compression: PNG or lossless WebP

According to MDN, lossy WebP files are on average 25–35% smaller than JPEGs of similar quality, and lossy AVIF files around 50% smaller. MDN also recommends a fallback for AVIF and WebP through the <picture> element: the browser takes the first format it supports, and everyone else gets the JPEG or PNG.

In practice, a site owner does not need to convert every photo by hand. Ask your developer or agency whether your CMS or CDN already serves modern formats, and check how large the files a phone actually receives are. A 4000-pixel photo squeezed into a 400-pixel product card is a common finding that no format will fix.

Dimensions that stop the page jumping

You start reading or reach for a button, and then a banner loads above it and pushes everything down. That is a layout shift, and Core Web Vitals measure it as CLS.

One common cause is images without dimensions: until the file arrives, the browser does not know how much room to leave. web.dev recommends adding width and height attributes to every <img> tag and says that leaving them out increases the images' impact on CLS. The attributes do not make an image rigid: responsive styles still scale it, and the browser simply knows its proportions in advance.

To check without tools, open a page on a phone with a slow connection and watch whether the text moves while photos appear. If it does, ask your developer to check dimensions in the product card, banner and gallery templates.

Lazy loading, but not for the hero image

The loading="lazy" attribute asks the browser to hold off loading an image until it gets close to the visible part of the screen. On long pages with galleries or a catalogue, that saves data and time. web.dev notes that browsers which do not support the attribute simply ignore it, and the default value is eager, meaning normal loading.

The key warning from the same article: do not lazy-load images that are likely to be visible as soon as the page opens, especially the main image that often becomes the LCP element, the largest thing on the first screen. A lazy hero banner starts loading later, so the page looks unfinished for longer.

A simple rule for templates: nothing on the first screen gets loading="lazy"; everything below it can. Check sliders and optimisation plugins in particular, since they often switch lazy loading on for every image without exception.

What FluxRadar checks

FluxRadar reads the HTML your server returns and the responses it receives while crawling:

  • Images without alt. A finding appears when an <img> has no alt attribute at all. An empty alt="" counts as correct for decorative images. The free check does this for the home page; Basic and Complete do it for every crawled page.
  • Broken images and media (Complete). A finding appears only when the crawl actually requested the file and got a 4xx or 5xx error, could not fetch it, or received an HTML page instead of an image. A file the crawl did not check is not reported as broken.

The tool does not judge whether alt text is well written, and it does not check file formats, width and height attributes or lazy loading. Review alt text and first-screen behaviour yourself on a few typical pages.
