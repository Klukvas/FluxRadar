Security headers without the jargon: HSTS, CSP and friends

What each common response header tells the browser, what your site risks without it, and the order to switch protection on so you do not block a form or a checkout.

Published and checked: November 16, 2026

"Security headers are missing" looks like a line for the developer. The decisions behind it belong to the site owner too: can someone reach the site over an unencrypted connection, can another site show your page inside a frame, and how much does the browser tell other sites about where a visitor came from. This article explains each header in plain words, gives the values that public guidance recommends, and points out where rushing can break a working site.

What a response header is

When a browser opens a page, the server sends more than HTML. It also sends response headers: short lines of instructions that the visitor never sees but the browser follows. Security headers are instructions such as "only ever load this site over HTTPS" or "do not show this page inside someone else's site".

Keep their limits in mind. A header does not fix a bug in your code and does not protect a logged-in area. It reduces the damage certain browser-based attacks can do. A missing header is a reason to review your configuration, not proof that the site has been compromised. Our article on public website audits covers what an outside scan can and cannot tell you.

You can look at the headers without any extra service. Open your browser's developer tools, go to the Network tab, reload the page, select the first request and read its response headers. Compare the homepage, a service or product page and a page with a form: different templates or even different servers may serve them, so their headers can differ.

HSTS: HTTPS only, even when someone types http

Strict-Transport-Security (HSTS) tells the browser to reach the host over HTTPS only. After the first secure visit, the browser upgrades any http address to https by itself and, as MDN describes, stops the visitor from clicking past a certificate error.

  • max-age is how many seconds the browser remembers the rule. A value of 0 removes the policy, but only once the browser receives that response over HTTPS.
  • includeSubDomains applies the rule to every subdomain. Before adding it, confirm that each subdomain, including an old staging host or a webmail address, works over HTTPS.
  • preload asks to be added to a list that browsers ship with. MDN notes that this list is not part of the specification and that it requires a max-age of at least one year plus includeSubDomains.

Browsers ignore HSTS sent over plain HTTP. The usual setup is therefore a permanent redirect from HTTP to HTTPS, with the header on the HTTPS response. OWASP warns that a misconfiguration or a certificate problem can lock visitors out for the whole max-age. Start with a short value, confirm everything works, and only then raise it to a year.

Three baseline headers for every HTML page

These headers are simple, rarely break anything and usually take one line in the server or CDN configuration.

Header What it does Value from OWASP guidance
X-Content-Type-Options Stops the browser from guessing a file type that contradicts what the server declared. nosniff
X-Frame-Options or CSP frame-ancestors Stops another site from embedding your page in a frame and covering it with misleading buttons. frame-ancestors where possible; otherwise X-Frame-Options: DENY
Referrer-Policy Controls how much of the page address the browser passes to the site a visitor goes to next. strict-origin-when-cross-origin

One caveat on framing: if partners deliberately embed your widget, calculator or form on their sites, a blanket ban will break it. In that case, list the allowed domains in frame-ancestors. Set Referrer-Policy explicitly rather than relying on the browser default, so you know that addresses with parameters, such as on-site search queries, are not passed in full to third-party services.

Content-Security-Policy without broken forms

Content-Security-Policy (CSP) is the most powerful header and the most demanding one. It lists where a page may load scripts, styles, images and other resources from. If an attacker manages to inject a script into a page, a well-built policy can stop it from running. OWASP calls CSP complex to configure and maintain.

The main risk is copying a strict policy from the internet. It will immediately block analytics, a chat widget, a payment form or inline scripts in your theme, and you may not notice straight away. A safer order:

  1. List your third-party services: analytics, ads, chat, payments, fonts, video, maps.
  2. Ship the policy as Content-Security-Policy-Report-Only. MDN describes this header as monitoring violations without enforcing the policy, so it blocks nothing.
  3. Collect reports with the report-to directive (MDN suggests also keeping the deprecated report-uri, because report-to does not yet work in every browser), then walk through the key journeys: enquiry, basket, checkout, login.
  4. Fix or explicitly allow the sources you need, and only then switch to the enforcing Content-Security-Policy header.

Review the policy every time you add a new service. It is part of normal site maintenance, not a one-off task.

Permissions-Policy, and headers you no longer need

Permissions-Policy switches off browser features your site does not use, such as the camera, the microphone and geolocation. OWASP gives the example geolocation=(), camera=(), microphone=(). For a brochure site or a shop this is a low-risk step: if you do not need a feature, a third-party script on the page cannot ask for it either.

The opposite also happens: older guides still recommend X-XSS-Protection. OWASP advises not setting it, or switching it off with 0, because that old browser mechanism could itself create vulnerabilities. Protection against injected scripts now comes from CSP. If a contractor offers to "add every security header on the list", ask them to explain what each one does for your site.

What FluxRadar checks and how to read a finding

Security headers are part of the Security module, which is included in the Complete plan. The checks are passive: FluxRadar reads the responses your site already sends to any visitor.

  • HSTS is checked on the homepage response of an HTTPS site. A finding appears when the header is missing or has no positive max-age. The rule does not apply to a site that runs on HTTP only.
  • Baseline headers are checked on every successful HTML page: X-Content-Type-Options: nosniff, framing protection (X-Frame-Options or CSP frame-ancestors) and a non-empty Referrer-Policy. The finding lists exactly what is missing.
  • CSP and Permissions-Policy are checked for a non-empty header. The automated check does not judge how strict the policy is.

Start by comparing pages. If a header is missing everywhere, it is easiest to add at the server or CDN level. If only some pages lack it, look for a separate template or subdomain with its own configuration. After the change, run the scan again and test forms and checkout by hand. A finding shows a missing signal. It does not prove an attack happened, and it does not replace an application test with agreed access.
