Redirect chains and 404s after a content clean-up

Removing outdated pages is easy. Deciding what someone who arrives at an old address should see, without leaving chains behind, takes more thought.

Published and checked: November 23, 2026

A content clean-up is worth doing: outdated news, finished promotions, discontinued products and several similar articles on one subject get in the way of visitors and of the team. But every removed address lives on somewhere: in bookmarks, old newsletters, other sites, internal links and search engine indexes. What happens to a person who follows one of those links is your decision. This article is about the reasoning behind those decisions. Our knowledge base has a step-by-step guide to checking them (in Ukrainian).

One decision for every removed page

Before deleting anything, write down what will happen to each address:

Situation Server response
A new page covers the same content a permanent 301 or 308 redirect to it
Several similar articles were merged into one a permanent redirect from each old address to the merged page
The page is gone only for a while a temporary 302 or 307 redirect
Nothing replaces it 404 or 410

The type of redirect matters. Google explains that its indexing system treats a permanent redirect as a signal that the new address should be the canonical one. A temporary redirect does not send that signal. Server-side redirects are the most reliable. Google recommends JavaScript redirects only when nothing else is possible, because the page might not be rendered.

It is tempting to send everything you removed to the home page. Google's site move guidance advises against it: many old addresses pointing at one irrelevant page confuse people and may be treated as soft 404s. The exception is when the content of several pages really has been merged into one.

An illustrative example: a shop removes the page for a model it no longer sells. If there is a newer version of the same model, a permanent redirect to it makes sense. If there is no direct replacement, a redirect to a general category only makes the visitor start searching again, and an honest 404 page with a link to the catalogue is more useful. And if the old page still holds a manual that owners of the product look for, it may be better not to remove it at all.

404 or 410: honesty matters more than the code

Both codes say the page is gone. MDN describes 410 as a resource that is no longer available and is likely to stay that way. If you do not know whether the removal is temporary or permanent, use 404.

For Google the difference is small: all 4xx codes except 429 are treated the same. Those addresses are not indexed, already indexed ones are dropped, and crawling of them gradually slows down. So pick the code that honestly describes the situation and that your CMS makes easy to set.

What matters more is that the response really is an error. A "Not found" page that returns a 200 code is a soft 404. The error page can and should still be useful, with search, links to the main sections or current offers. That does not change the response code.

You can check the real code in the browser's developer tools: the Network tab shows the status of every request. A link checker or an audit tool shows the same for many addresses at once.

How chains grow over the years

Nobody builds a redirect chain on purpose. Take an illustrative example. Years ago the site moved from http to https. Later it dropped www. Then the News section was renamed Blog, and after a redesign the address structure changed again. Each time, a new rule was added on top of the old ones. Someone opening a link from an old email now passes through three or four hops before they see the page.

Google says its crawlers follow up to 10 redirect hops by default, and other Google products may set different limits. Its site move guidance still recommends redirecting straight to the final destination and, where that is not possible, keeping the chain short: ideally no more than three hops and fewer than five. Every hop is another request the visitor waits for.

The fix is simple to describe: rewrite the old rules so each one points directly at the final address, and update internal links so they do not go through redirects at all. Also look for loops, where address A redirects to B and B back to A: such a page never opens.

A clean-up can easily create a new chain: you redirect an article to the merged page without noticing that two older addresses already redirect to that article. Before adding a rule, check whether the old address is the destination of other rules, and point those straight at the new final address.

Checking the site after a clean-up

  1. Before the clean-up, list the addresses you are removing or moving. Sources: the old sitemap, a CMS export, landing pages in your analytics, and addresses other sites link to.
  2. For each one, write down the expected behaviour: where it redirects or which code it returns.
  3. After launch, check the actual chain: the code of every hop and the final address. A redirect should end in a 200 response, a removed page in 404 or 410.
  4. Find internal links to removed pages and to old addresses that now redirect, and fix them in menus, text and templates.
  5. Take removed addresses out of the sitemap.
  6. Do not rush to delete the rules. Google's site move guidance says to keep redirects for as long as possible, generally at least a year.

Internal links matter beyond redirects too: our article on internal linking explains how to make sure important pages stay reachable after the structure changes.

What FluxRadar checks

  • Redirect chains and loops. An address that reached its final response through two or more redirects is reported with every hop and its status code. A single redirect is treated as normal. A loop, or a chain longer than the crawl limit, is a separate finding.
  • Internal links to pages that return a 4xx or 5xx error. The finding is shown on the page that carries the link. Only targets the crawl actually visited are judged.
  • Pages that do not answer with HTTP 200. When the crawl reaches a page whose final status is 400 or higher.

The crawl cannot discover old addresses that nothing links to any more. You can add them as start URLs; they follow the same scan scope, robots.txt rules and page limit. If you add an address you removed on purpose, the report will show it as an error page, and in that case that is the expected result. FluxRadar has no separate soft 404 rule, so check "not found" pages that return 200 by hand.
