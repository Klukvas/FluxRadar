# Исследование надёжности запусков Claude-агентов

Дата исследования: 2026-09-06

## Краткий вывод

Мы несколько раз называли запуск «зависшим» только потому, что в наблюдающем терминале долго не появлялся финальный текст. Это недостаточное доказательство: Claude Code может быть жив, выполнять tool-команды или стримить события, которые текущий способ ожидания не показывает.

Проблема состоит не в одной неисправности Claude, а в отсутствии у запуска формального жизненного цикла: heartbeat, состояния, дедлайна, проверки финального результата и диагностики дочерних процессов. Кроме того, часть запусков выполнялась напрямую через `claude`, минуя репозиторный wrapper, поэтому заявленный протокол checkpoints и JSONL-логи не применялись.

## Проверенные факты

### 1. Wrapper существует, но не является watchdog-ом

Источник: [`scripts/run-claude-agent.sh`](../../scripts/run-claude-agent.sh).

Скрипт:

- добавляет текстовый протокол `STARTED`, `PLAN_READY`, `CODE_READY`, `TESTING`, `DONE`, `BLOCKED`, `FAILED`;
- запускает `claude --print --verbose --output-format stream-json --include-partial-messages`;
- передаёт stdout в `tee` и сохраняет JSONL-файл;
- возвращает exit code Claude через `PIPESTATUS`.

Но скрипт не делает следующего:

- не устанавливает `max-budget-usd`;
- не имеет wall-clock timeout или watchdog;
- не записывает PID, состояние и heartbeat в отдельные файлы;
- не разбирает stream-события и не обновляет состояние по ним;
- не отличает «Claude выполняет tool» от «Claude заблокирован»;
- не проверяет наличие обязательного финального checkpoint/result;
- не захватывает stderr в JSONL-лог;
- не завершает дерево дочерних процессов по дедлайну;
- не блокирует одновременную запись нескольких агентов в один рабочий tree.

Поэтому это logging wrapper, но не надёжный supervisor.

### 2. Документированный stop policy остаётся ручным

Источник: [`docs/AGENT_CHECKPOINTS.md`](../AGENT_CHECKPOINTS.md), строки 17–32.

Документ правильно говорит не останавливать агента только из-за тишины и проверять процесс, изменения в worktree, дочерние команды и checkpoints. Однако эти проверки описаны как инструкция оператору. Автоматического механизма, который выполняет их и переводит запуск в `running`, `blocked`, `failed`, `timed_out` или `completed`, нет.

### 3. CLI умеет стримить события, но это должно быть частью протокола

Источник: локальный `claude --help`, версия `2.1.236`.

CLI поддерживает `--output-format stream-json`, `--include-partial-messages`, `--verbose`, `--debug-file`, `--max-budget-usd`, `--no-session-persistence`, `--fallback-model` и другие параметры, необходимые для наблюдаемого запуска.

Контролируемый no-op probe в обычном режиме с `--output-format stream-json --include-partial-messages` вернул:

1. `hook_started` / `hook_response`;
2. `init`;
3. `status: requesting`;
4. `stream_event` с partial text;
5. финальный `result` с `PROBE_OK` и exit code 0.

То есть CLI в рабочем режиме умеет отдавать промежуточные события. Если оркестратор их не видит, проблема находится в способе запуска/сбора/ожидания, а не обязательно в модели.

Контролируемый probe с `--bare` завершился за 47 ms с `authentication_failed` и `apiKeySource: none`. Это не зависание. `--bare` намеренно отключает keychain и часть пользовательской конфигурации, поэтому его нельзя использовать как обычный fallback без явно переданной авторизации.

### 4. Обычный запуск загружает внешние зависимости до работы агента

В обычном probe были видны startup hook, плагины и MCP-серверы: Obsidian подключён, Google Drive/Gmail/Calendar находятся в состоянии `needs-auth`. По документации CLI, `--bare` и `--safe-mode` отключают часть hooks, LSP, plugin sync, MCP/кастомизаций.

Следствие: задержка до первого полезного события может быть связана не с моделью, а с hook/plugin/MCP/auth/network startup. Это отдельное состояние `starting`, его нельзя смешивать с `thinking` или `blocked`.

### 5. В текущем запуске старый интерактивный Claude-процесс не доказывает зависание

Был найден процесс `claude` с PID `56804`, живущий около 3 дней. Он привязан к `ttys007`, имеет интерактивный shell-родитель и открытые сетевые соединения. Это похоже на оставленную интерактивную сессию, но без просмотра её терминала нельзя утверждать, что она зависла. Автоматически завершать такие процессы опасно.

### 6. Вспомогательный research-agent повторил проблему наблюдаемости

Независимый read-only агент был запущен с узкой задачей и должен был создать этот отчёт. За несколько ожиданий суммарно более двух минут он не отдал финальный статус, не показал checkpoint и не создал артефакт. Его статус оставался `running`; затем он был остановлен после проверки отсутствия отчёта.

Это не доказывает, что он был вычислительно зависшим. Но это доказывает, что текущий интерфейс ожидания не позволяет отличить «работает» от «застрял», и именно поэтому оператор начинает перезапускать агентов вслепую.

## Причины в порядке приоритета

1. **Ложный positive на зависание из-за отсутствия наблюдаемого heartbeat.** Тишина stdout или timeout вызова ожидания не равны остановке процесса.
2. **Нет supervisor state machine.** Нет единого источника правды с PID, временем последнего события, текущей фазой и причиной завершения.
3. **Не все запуски используют wrapper.** Прямые вызовы Claude не создают ожидаемый run log/checkpoint-контур.
4. **Нет дедлайна и безопасного завершения process group.** Процесс может остаться живым, а оркестратор — потерять контроль над ним и его дочерними командами.
5. **Не отделены startup, model work, tool execution и verification.** Hook/MCP/plugin/network задержки выглядят как одна и та же «зависшая» задача.
6. **Общий dirty worktree допускает конкуренцию агентов.** Даже работающий агент может казаться безрезультатным, если другой агент меняет те же файлы, запускает тесты или оставляет процессы.
7. **Нет обязательного машинно-проверяемого результата.** Финальный текст агента не должен быть единственным доказательством выполнения.

## Какой протокол нужно внедрить

### Состояния запуска

Минимальная state machine:

`queued → starting → running → verifying → completed`

Отдельные terminal states:

`blocked`, `failed`, `timed_out`, `cancelled`.

`running` должен иметь `last_event_at`, `last_checkpoint`, PID, список дочерних PID и `worktree`/lock. Состояние считается подозрительным только после таймаута heartbeat, а не из-за отсутствия финального текста.

### Артефакты каждого запуска

Для каждого `run_id` нужен отдельный каталог, например `/tmp/fluxradar-agent-runs/<run_id>/`, с файлами:

- `status.json` — состояние, timestamps, PID, exit code, last event/checkpoint;
- `stdout.jsonl` — полный stream-json;
- `stderr.log` — stderr и ошибки wrapper;
- `result.md` — обязательный финальный отчёт агента;
- `changed-files.txt` — снимок изменений;
- `checks.txt` — фактически выполненные проверки.

Финальный успех разрешён только если процесс завершился с exit code 0, был получен валидный result, присутствует `DONE` и выполнены требуемые проверки.

### Watchdog

Wrapper должен:

1. запускать Claude в отдельной process group;
2. читать stream-json и обновлять `status.json` на каждом событии;
3. распознавать checkpoints из assistant text;
4. отдельно контролировать startup timeout, idle heartbeat timeout и общий hard deadline;
5. при deadline сначала отправлять TERM всей process group, затем после grace period KILL;
6. сохранять диагностику перед завершением;
7. не делать автоматический restart после любого timeout — сначала классифицировать причину.

Рекомендуемые значения для coding-задач: heartbeat 90 секунд, предупреждение после 120 секунд, общий deadline 30 минут. Значения должны быть настраиваемыми, а не зашитыми в prompt.

### Изоляция

Один coding-agent должен работать в отдельном worktree или под эксклюзивным lock на репозиторий. Review-agent должен быть read-only или работать в отдельной копии. Это устраняет гонки, когда несколько агентов одновременно правят одни и те же файлы.

### Политика retry

Retry допустим только для классифицированных временных ошибок: network reset, rate limit с retry-after, временный auth/backend error. Не надо перезапускать задачу, если процесс жив и heartbeat обновляется. Не надо повторять задачу после неизвестного timeout без сохранённого run state — иначе можно получить дублирующие изменения и двойные расходы.

## Приоритет следующей реализации

1. Переделать `scripts/run-claude-agent.sh` в supervisor с `status.json`, раздельными stdout/stderr и hard deadline.
2. Добавить обязательный `result.md`/структурированный result и проверку `DONE`.
3. Добавить process-group cleanup и диагностику дочерних процессов.
4. Принудить все запуски Claude проходить через wrapper; прямые команды оставить только для диагностики.
5. Добавить lock/worktree isolation.
6. После этого провести три теста: успешная задача, намеренно длинная задача с heartbeat и намеренно заблокированная задача. Проверить, что каждая получает правильный terminal state без ручного угадывания.

## Что изменено в ходе исследования

Продуктовый код не изменён. Добавлен только этот исследовательский отчёт. Старый интерактивный процесс `PID 56804` не завершался, потому что имеющихся данных недостаточно, чтобы считать его зависшим.
